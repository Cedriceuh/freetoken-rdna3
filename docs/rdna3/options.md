# Options

Every tunable this build adds on top of upstream FreeToken is switched by an environment variable (set it in a
profile, or with `-e` on `docker run`). Unless stated otherwise the default is upstream's behavior. A few fixes have
no switch: the ROCm sampling routes, CUDA graphs for every batch size up to an explicit `--cuda-graph-max-bs` (8 or
less), the GDN boundary carried across prefill chunks, the TP>1 relay handshake, the refusal of a cache rebuild under
an uneven split, and RCCL instead of PyNCCL on ROCm ([limits.md](limits.md#does-it-work-on-nvidia-gpus)).
Measurements are from the reference machine (RX 7900 XTX + RX 7900 XT, TP=2), with the Qwen3.8-Flash-Next NVFP4
checkpoint unless a row names another. Each option's effect was measured on the build that added it, as an A/B of that
option (a row says when something else changed with it): compare its two arms with each other, not with
[benchmarks.md](benchmarks.md). The runs behind them, with their dates: [journey.md](journey.md).

The labels:

- **Bit-exact**: the same results as without the option (identical greedy answers on a fixed set of 120 prompts, or a
  kernel check with identical outputs).
- **Reorders sums**: the same math, but floating-point additions happen in another order, so answers can differ at
  rounding level without being worse.
- **Lossy**: the numbers themselves change (8-bit weights).
- ***Agent-validated***: part of the two-card builds that scored 12-13 on the author's private agentic benchmark (29
  planted bugs, long OpenCode sessions; see [benchmarks.md](benchmarks.md#precision)). The one-card profiles were not
  run on it. `FREETOKEN_TP_SPLIT`, `FREETOKEN_INT8_DENSE`, `FREETOKEN_FUSE_MOE_ALLREDUCE` and `FREETOKEN_TRITON_GEMV`
  were also checked on a 671-item scored benchmark.

For every `ft serve` flag, see upstream's [CLI reference](../cli.md); the flags the profiles use are explained in
[profiles.md](profiles.md).

## Two or more GPUs

| Variable | Default | Effect |
|---|---|---|
| `FREETOKEN_TP_SPLIT` | unset (even) | Uneven tensor parallelism: rank 0's share at TP=2 (`0.55`) or one weight per rank (`11:9`). XTX + XT at `0.55`: +4 % decode. With an EXL3 checkpoint the expert slices round to whole 128-wide blocks (`0.55` gives 384 / 256, the even split is refused). Reorders sums (and, with `FREETOKEN_INT8_DENSE=1`, changes the int8 scales of two layers: see below), *agent-validated*. |
| `FREETOKEN_TP_ALLOW_IMBALANCE` | unset | `1`: accept ranks whose free memory differs by more than 2 GiB (upstream refuses them) and plan every pool on the smallest one. Needed for unequal cards; below a 2 GiB difference it changes nothing. |
| `FREETOKEN_HOST_ALLREDUCE` | unset | `1` (two ranks, ROCm): small all-reduces through one shared host-memory region and a one-block kernel instead of RCCL's proxy path. 6 µs instead of ~12 µs per decode all-reduce, **+2.5-4.8 % decode, bit-exact** (fp32 accumulation, rounded to bf16 like RCCL). |
| `FREETOKEN_HOST_ALLREDUCE_MAX` | `262144` | Largest message (bytes) that takes the host path; bigger ones stay on RCCL. |
| `FREETOKEN_HOST_ALLREDUCE_UNCACHED` | `1` | Register the shared pages as uncached fine-grained memory (`0`: default registration). |
| `FREETOKEN_HOST_ALLREDUCE_TIMEOUT_S` | `300` | How long a rank waits for its peer before trapping (a desynchronized pair must not hang forever); `0` = wait forever. |
| `FREETOKEN_HOST_ALLREDUCE_WAITLOG` | unset | Debug, `1`: each call stores how long its rank waited for the other one (100 MHz ticks, `[rank][seq % 65536]` after the four slots), and the shared region stays in `/dev/shm` (`freetoken-hostar-*-waitlog`) for a reader inside the container until a clean shutdown (a killed container leaves it: `--ipc=host` puts it in the host's `/dev/shm`, owned by root). Same speed. On `xtx-xt` it showed the XTX waiting ~0.9 ms a decode step for the XT, at every all-reduce. |
| `FREETOKEN_TP_SYNC_TOKENS` | `1` | `1` broadcasts rank 0's sampled tokens to the other ranks after each sampled step (~15 µs per step). `0` = off; `check` also compares the ranks' draws and logs each disagreement (one sync per step). |
| `FREETOKEN_FUSE_MOE_ALLREDUCE` | `1` | qwen4_exp at TP>1: one all-reduce per MoE block (routed + shared experts) instead of two. +2.7 % decode, -4.5 % prefill time. Reorders sums, *agent-validated*. |
| `FREETOKEN_PREFILL_AR_OVERLAP` | `1` | qwen4_exp at two ranks, with `FREETOKEN_FUSE_MOE_ALLREDUCE` and the fused MoE epilogue (offloaded NVFP4 or EXL3 experts decoded on the GPU: not with `--hybrid`): a prefill chunk whose routed experts run in token blocks (`FREETOKEN_NVFP4_PREFILL_BLOCK`, `FREETOKEN_EXL3_PREFILL_BLOCK`) starts each block's all-reduce while the next block computes, instead of one all-reduce after the last block. Each element is the same epilogue, then the same sum of the two ranks' values: **bit-exact** (`tests/moe/test_prefill_block_hook.py`). Cold reads on `xtx-xt-4x262k` 4-6 % shorter (NVFP4 164k tokens 70.1 -> 67.0 s, EXL3 3.05 bpw 66.6 -> 62.8 s). The engine synchronizes the device once before the next decode step: without it the decode graphs ran a third slower at four requests. `0`: one all-reduce after the experts. |
| `FREETOKEN_GDN_AR_OVERLAP` | `1` | qwen4_exp at two ranks, the output projection bf16 or int8 weight-only: in a prefill chunk of one request made of whole `FREETOKEN_GDN_PREFILL_BLOCK` blocks (every 16k-token chunk of a long read but its last), each GatedDeltaNet block's gated norm and output projection run as its delta rule finishes, and that block's all-reduce starts while the next block's delta rule runs. hipBLASLt keeps the rows' bits for some shapes and block sizes only, so the first chunk of each length checks block against whole call on random data, and the ranks keep the overlap for that length only if all of them pass: **bit-exact** (`tests/models/qwen4_exp/test_gdn_ar_overlap.py`). Cold reads on `xtx-xt-4x262k`, after `FREETOKEN_PREFILL_AR_OVERLAP`, ~1-1.6 % shorter (NVFP4 164k tokens 66.9 -> 65.8 s). The check takes ~0.2 GiB for a moment, once per chunk length. `0`: the output projection after the last block. |
| `FREETOKEN_RELAY_HANDSHAKE_MAX_HELLOS` | `2400` | TP>1: how many 50 ms hellos the rank-0 relay sends while the other ranks subscribe (2 minutes). |

**`FREETOKEN_TP_SPLIT`** splits the experts' intermediate dimension (routed experts on the NVFP4 Triton expert kernels,
and the shared expert) and the GatedDeltaNet heads, the last two on qwen4_exp (Qwen3.8-Flash-Next's model code, the
only one tested); attention, the vocabulary and the PLE stay even or replicated
([how-it-works.md](how-it-works.md)). Each rank then holds a smaller or larger share of every expert, and because the
ranks all use the smallest card's expert-cache plan, the XT's smaller share raises the number of cached experts on
both cards (7,683 -> 8,708 slots when it was measured). With int8 dense layers the split also changes the int8 scales
of the two row-parallel layers it cuts unevenly (GDN output and shared-expert down projections), not only the order
of the sums.

**`FREETOKEN_TP_SYNC_TOKENS`**: every rank samples its own copy of the logits, so two different GPUs could in principle
continue on different tokens; the broadcast makes rank 1 follow rank 0. It changes no answer while the ranks agree (0
disagreements over ~8k sampled tokens in `check` mode). It is on the torch.distributed path (ROCm always; NVIDIA with
`--disable-pynccl`), and was not run on the agentic benchmark.

## Dense layers

| Variable | Default | Effect |
|---|---|---|
| `FREETOKEN_INT8_DENSE` | unset | `1`: every dense (non-expert) linear layer in int8, weights only, one scale per output channel and rank; routers and the vision tower stay bf16. Converted at load. **+28 % decode**, frees ~2.4 GiB per card for the expert cache. Lossy, not bit-exact; no measurable loss on the scored benchmark, *agent-validated*. |
| `FREETOKEN_INT8_DENSE_SKIP` | empty | Comma-separated module names to keep in bf16. |
| `FREETOKEN_INT8_PREFILL_DEQUANT` | `triton` | With `FREETOKEN_INT8_DENSE=1`, a prefill dequantizes each int8 weight for its GEMM in one Triton pass (int8 times the row's fp32 scale, rounded once to bf16) instead of `torch.mul`'s mixed-dtype kernel: the same arithmetic, **bit-exact** (`tests/kernels/test_int8_dequant.py`). The dequant 2-8x faster on the 7900 XT (GDN in_proj 456 -> 58 us); agent turns 0.7-1.6 % shorter on `xtx-xt-4x262k`. `torch`: `torch.mul`. |
| `FREETOKEN_INT8_COMPACT` | `1` | Compact the device allocator after the conversion; without it the freed VRAM stays fragmented and is lost to the expert cache. |
| `FREETOKEN_EMBED_HOST` | `1` on ROCm, `0` elsewhere | The input embedding, when it is not tied to the LM head (Qwen3.8-Flash-Next's is not), stays in pinned, device-mapped host memory instead of VRAM: the same lookup kernel reads the same rows across PCIe, a 5 KiB row per token. Its VRAM (606 MiB a rank at TP=2, 1.18 GiB on one card) goes to the expert cache: on `xtx-xt-4x262k` (a 3 x 262k pool) 8,768 -> 9,255 slots with NVFP4 and 11,554 -> 12,095 with EXL3 3.05 bpw, on `xtx` 4,783 -> 5,459 (EXL3); decode 1-6 % faster, agent turns ~3 % shorter, cold reads unchanged. The same bits (`tests/layers/test_embed_host.py`). The server locks 1.2 GiB more RAM (the table). `0`: the table in VRAM. |
| `FREETOKEN_INT8_ROWS_MAX` | `8` | Decode batches up to this many rows (concurrent requests) use the row-looped GEMVs (the int8 one and the bf16 Triton one), each row bit-identical to a batch of one; bigger batches dequantize the int8 weight per call (bf16 layers use `F.linear`). |
| `FREETOKEN_INT8_ROW_GROUPS` | `1` | With several rows (a speculative verify step, or requests decoding together), the int8 GEMVs whose input is longer than one tile (hyper-connection down projections, shared expert gate/up, index projection, LM head) read each weight tile once for up to 4 rows instead of once per row; same arithmetic per row, bit-exact. At 4 rows on the XT: HC down 17.7 -> 12.1 µs, LM head 704 -> 499 µs. `0`: each program runs the rows one after the other, reloading the tile for each. |
| `FREETOKEN_INT8_TP_TILES` | unset | `1` (opt-in, **not bit-exact**): K blocks of 512 for three int8 shapes of the uneven split (GDN in_proj 9270 / 7210 x 2560, attention qkv), which then run 2-4 verify rows through the row-group kernel, and an 8-wide tile for the HC up projection. Forward pass -1.5 / -2.6 / -2.9 % at 2 / 3 / 4 rows, -2.3 % at four requests on `xtx-xt-4x262k`. Each row is summed in another order, so greedy answers change at rounding level (6 of 14 prompts); not run on the agentic benchmark. |
| `FREETOKEN_HC_SILU_EPILOGUE` | `1` | Int8 decode rows: the hyper-connection's down projection stores its low-rank columns through `hc_silu` and the up projection reads them in place, instead of a kernel of its own in between (two per layer). Same bits; EXL3 3.05 bpw `xtx-xt-4x262k` +1.2 % decode at one request, +1.9 % at four; NVFP4 `xtx-xt` +1.1 % and +1.1 %. `0`: the separate kernel. |
| `FREETOKEN_HC_MIX_IN_GEMV` | `1` | Int8 decode rows, with the epilogue above: the hyper-connection's up projection mixes its gates into the streams as it computes them (`hc_gate_mix` inside the GEMV, its expression and stream order kept; each stream's weight row loaded once for all the rows), instead of a kernel of its own (two per layer). Same bits. At one request / four: EXL3 3.05 bpw `xtx-xt-4x262k` +0.6 % / +1.4 %, NVFP4 `xtx-xt` +0.5 % / +1.1 %. `0`: the separate kernel. |
| `FREETOKEN_SHARED_ACT_IN_GEMV` | `1` | Int8 decode rows: the shared expert's gate \| up projection stores SiLU(gate) x up (a program computes its gate columns and the matching up columns), instead of a SiLU-and-mul kernel after it (one per layer); only where the Triton activation is the reference (no flashinfer), and past 2 rows only for shapes whose K fits one tile. Same bits. EXL3 3.05 bpw `xtx-xt-4x262k` +0.8 % / +1.3 % at one / four requests, NVFP4 `xtx-xt` +0.1 % / -0.1 %. `0`: the separate kernel. |
| `FREETOKEN_MOE_COPY_OVERLAP` | unset | `1`: in decode, the copy of the missing experts goes to a side stream ahead of the shared expert and its gate; the expert GEMVs wait for it (offload backend, GPU decode, Qwen3.8-Flash-Next). Bit-exact, but slower end to end: 47.5 tok/s decode against 71.1 without it (-33 %; one request, agent turns at 77-99k of context, MTP head on) and cold reads 13 % longer, cause not found. Leave it off. |
| `FREETOKEN_TRITON_GEMV` | `1` on gfx11 | Split-K Triton GEMVs for the bf16 decode shapes of RDNA3 (other GPUs: off). +3.5 % decode on the bf16 build; with `FREETOKEN_INT8_DENSE=1` only the routers are still bf16 and use it. Reorders sums (split-K), *agent-validated*. |
| `FREETOKEN_GEMV_LAST_REDUCES` | `1` | For a bf16 Triton GEMV split over K (the MoE router: 4 splits), the last of a tile's programs to finish sums the partial results (element by element, in split order, as the separate reduce kernel did) instead of a second launch; an atomic counter per tile, reset by that program. **Bit-exact**, 48 launches fewer per decode step; measured together with `FREETOKEN_FEWER_COPIES` below. `0`: the reduce kernel. |

## Experts (MoE)

| Variable | Default | Effect |
|---|---|---|
| `FREETOKEN_NVFP4_PREFILL_TUNED` | unset | `1`: NVFP4 expert GEMM tiles for prefill swept on RX 7900 XTX / XT for this model, chosen by token count (any split, one or two cards). Only the M / N tiles, warps and stages change (a different K tile would reorder the sums): **bit-exact**, the bits of upstream's default tiles (16 to 8192 tokens, checked on one card). One prefill MoE block of 1600-2560 tokens 2.8-3.0x faster than the tiles it replaced, 1280 tokens 1.4-1.5x; prefills of up to 1536 tokens (agent turns, a few rows an expert) take 4-warp tiles (NVFP4 one-word turns at 26k 0.350 -> 0.227 s on `xtx-xt-4x262k`, an earlier build); long prompts -11 % on the prefill GEMM before upstream's rewrite. |
| `FREETOKEN_NVFP4_DECODE_TUNED` | unset | `1`: the same for decode (upstream's marlin decode kernel), per (N, K) and batch size, for the two-card shapes at a 0.55 split; other shapes (one card, other splits) keep the default tiles, logged once per shape. The down GEMV x1.06-1.19 in the kernel sweep (gate_up keeps the default tiles, the best of the sweep). **Bit-exact** against the default tiles. |
| `FREETOKEN_NVFP4_PREFILL_BLOCK` | `4096`; `8192` in the `xtx-xt` and `xtx-xt-4x262k` profiles | The prefill MoE runs the chunk this many tokens at a time on the same expert banks (`0` = the whole chunk). The block size changes no bit (`rdna3/tests/moe_block_check.py`, both cards; greedy answers and an agent conversation identical at 8192 and 16384). Its temporaries grow with it, ~75 KiB a token on the 7900 XTX's slice (~600 MiB at 8192), and the cache planner does not set them aside. 8192 instead of 4096: cold reads +7.9 % (arms alternated, an earlier build); 16384 read faster again but left the XT 0.65 GiB of VRAM at the peak of a 255k-token read, hence 8192. One card keeps 4096 (8k chunks, less working memory). |
| `FREETOKEN_NVFP4_PREFILL_TAIL_TILES` | `1` | With `FREETOKEN_NVFP4_PREFILL_TUNED=1`, a prefill block of more than 6144 tokens: each expert's rows past its last full 128-row tile run in 32-row tiles of a second launch, in both GEMMs, instead of a 128-row tile mostly padding (an expert gets ~160 rows of an 8192-token block on average). Only the M / N tiles, warps and stages change: **bit-exact** (`tests/moe/test_prefill_tail_tiles.py`). One 8192-token MoE block 16-19 % faster with random routing, 11-12 % with this model's own; cold reads of 113-210k tokens ~5-6 % shorter on `xtx-xt-4x262k`, between two earlier builds that also differed by `FREETOKEN_ROW_STORE_RINGS` (which alone moves such reads by 1 % at most). `0`: one launch of 128-row tiles (64 for the down GEMM). |
| `FREETOKEN_EXL3_MID_COLS` | `32` | EXL3: in prefill (more than 256 routes, fp16), the step between the two expert products rotates 32 columns of the Hadamard at a time, 32 rows and 4 warps a program, instead of 64-row tiles. **Bit-exact** (`tests/kernels/test_exl3_mid_cols.py`); 1.7-3.3x faster, with 572 B of scratch per lane instead of the tile kernel's 2.7 KB (a dispatch of it waiting for that scratch once held a rank before an all-reduce until the 60 s watchdog: [journey.md](journey.md#27-agent-turns-short-prefills-through-the-expert-cache-2026-10-14)). `0`: the tile kernel. |
| `FREETOKEN_EXL3_PREFILL_BLOCK` | `4096` | EXL3 checkpoints ([how-it-works.md](how-it-works.md#exl3-checkpoints)): the prefill MoE runs 4096 tokens at a time (`0` = the whole chunk); its temporaries (540-620 MiB on the 384-wide expert slice) are kept free by the cache planner at start. The block size changes no result (`rdna3/tests/exl3_moe_check.py`), except that a block of 25 tokens or fewer (the last one included) takes decode kernels for some of its steps and rounds differently. 8192 read 2-2.5 % faster but left 504 fewer expert slots (of 11,117), hence 4096. Blocks of up to 512 tokens (agent turns) run 16-row tiles instead of 32 (always on, the same bits): the MoE block 11-19 % faster at 32-512 tokens. |
| `FREETOKEN_EXL3_PREFILL_TAIL_TILES` | `1` | EXL3 checkpoints, a prefill block of 3072 tokens or more: the gate-up GEMM runs each expert's full 64-row tiles in one launch and its remaining rows in 32-row tiles in a second one (the down GEMM keeps its 32-row tiles: no gain there). The same K order: **bit-exact** (`tests/moe/test_prefill_tail_tiles.py`). Cold reads of 113-210k tokens 1.4-1.6 % shorter on `xtx-xt-4x262k`. `0`: one launch of 32-row tiles. |
| `FREETOKEN_HYBRID_FETCH_FRACTION` | unset | With `--moe-strategy hybrid` ([cpu-experts.md](cpu-experts.md)): the share of each decode step's expert misses fetched over PCIe (strictly between 0 and 1), the rest computed on the CPU, the same share on every MoE layer (`rdna3/serve.sh --hybrid` sets `0.25` on one card and `0.4` on two with NVFP4, `0.6` with EXL3). Unset: the split `ft bench bw --model <checkpoint>` measured for each layer's kind, or a fixed cap of one fetch per layer without one (EXL3 is not benched). |
| `FREETOKEN_HYBRID_MIN_REQS` | `1` | With `--moe-strategy hybrid`: decode steps of fewer requests fetch every miss (the offload path). CUDA graphs are captured per batch size, so each size takes one path. `rdna3/serve.sh --hybrid` does not set it. |
| `FREETOKEN_HYBRID_FLAG_IN_KERNEL` | `1` | With `--moe-strategy hybrid`: one kernel writes the CPU's inputs into its pinned IO rows and rings the coordinator, another waits for the CPU's partial and adds it back, over two pinned flag words (`0`: upstream's copies around the doorbell's stream memops, ~3.2 us a node). Bit-identical. With the other hybrid kernels, one request on NVFP4 `xtx-xt` 74.3 -> 78.3 tok/s, measured with an earlier handshake that these replaced, not again since ([cpu-experts.md](cpu-experts.md)). Replaces `FREETOKEN_HYBRID_SPLIT_KERNEL`. |
| `FREETOKEN_CPU_MOE_GROUP` | `1` | CPU expert executor, NVFP4 / bf16: one task per (expert, row block) for the routes of rows that share an expert, so its rows are read from RAM once (`0`: one task per route). Bit-identical. |
| `FREETOKEN_CPU_MOE_ROUTE_STATS` | unset | Measurement: every `n` CPU expert tasks, print how many of the CPU's routes repeat an expert of another row of the same step (8-13 % in the `--hybrid` runs). |
| `FREETOKEN_HYBRID_SKIP_CPU_ROUTES` | `1` | With `--moe-strategy hybrid`, NVFP4 and EXL3: the GPU decode kernels write zeros for the routes the CPU computes (slot -1) instead of computing them on slot 0 at weight 0. Bit-identical; +1-3 % decode ([cpu-experts.md](cpu-experts.md)). |
| `FREETOKEN_CPU_MOE_CORES_BY_SLICE` | `0` | `1`: under tensor parallelism each rank's CPU expert pool takes a share of the cores proportional to its expert slice (an uneven `FREETOKEN_TP_SPLIT`) instead of half. Measured without gain. |
| `FREETOKEN_CPU_MOE_SMT` | `0` | `1`: the CPU expert pool also runs on its cores' SMT siblings. 5-11 % faster alone on the CPU (EXL3), 14-42 % slower in serving. |
| `FREETOKEN_CPU_MOE_EXL3_COLS` | `1` | EXL3 on the CPU: adjacent tile columns per task, the first prefetching their contiguous row segments. 7-8 % less CPU time on 31 threads alone, within the noise in serving. |
| `FREETOKEN_BATCH_MEMCPY_ROCM` | unset | Copy engine for `--moe-prefill-hit-d2d` on ROCm: `batch` = `hipMemcpyBatchAsync` (HIP >= 7.1), `loop` = one copy per entry (full-layer short prefills ~10 % slower); unset tries `batch`, then `loop`, and logs a mode that fails its probe. |
| `FREETOKEN_PREFILL_HIT_LOG` | unset | `1`: log, per prefill chunk, the share of expert rows reused from the GPU cache instead of crossing PCIe. |
| `FREETOKEN_PREFILL_CACHED_MAX` | `1280` for Qwen3.8-Flash-Next, `0` otherwise | A prefill chunk of at most this many tokens (an agent's tool result) reads its routed experts through the slot cache: only the ones it lacks cross PCIe, those the next layer is predicted to need copied while this one computes (`FREETOKEN_PREFILL_PREDICT`), instead of streaming every expert the cache lacks through the full-layer buffers; `0` = off. Decided once per forward, so every layer takes the same path; off when a layer is a CPU or unpinned one, or when the expert cache is several slot pools or holds fewer slots than two layers of experts. The same bits; the experts it brings in are the next to be evicted, so the decode after the turn keeps its cache. EXL3 3.05 `xtx-xt-4x262k`, 25k of context, measured with a top-14 prediction (`FREETOKEN_PREFILL_PREDICT_EXTRA=4`; the default top-10 is faster still: see `FREETOKEN_PREFILL_PREDICT`): 132-339-token turns 0.76-0.79 -> 0.50-0.56 s to their first token, ~1k-token turns 0.84-0.88 -> 0.76-0.82 s, unchanged above the threshold ([journey.md](journey.md#27-agent-turns-short-prefills-through-the-expert-cache-2026-10-14)). Under `--hybrid` the answers then move, as any change of the cache's contents moves them there ([cpu-experts.md](cpu-experts.md)). |

## Qwen3.8-Flash-Next specifics

| Variable | Default | Effect |
|---|---|---|
| `FREETOKEN_PLE_SYNC` | `auto` | How a captured decode step gets its PLE disk rows. `auto` probes the stream memops once at start: `wait-sync` (the step waits inside the graph for the host fill) where a captured wait holds three replays in a row (ROCm 10 on these cards); else `launch-gating` (the host fills before each launch). On one GPU without the MTP head (the scheduler then overlaps its decode steps) `auto` takes `launch-gating`: wait-sync costs ~11 ms a step there (NVFP4 `xtx --no-mtp`: 26.6 tok/s against 38.3). The log says which. `wait`: require memops, `gate`: never use them. Elsewhere wait-sync gives +1.6-4.3 % decode over launch-gating, bit-exact. |
| `FREETOKEN_PLE_PREFILL_PREFETCH` | `1` | With `--ple-backend disk` (every profile): a thread reads a prefill's PLE rows from the checkpoint while the layers before the PLE layer launch (the lookup waits for them), and while a chunk of a longer prompt computes it reads the next chunk's rows into the other pinned buffer, instead of a read before each forward with the GPUs idle (~1.1 s for a 16k-token chunk on the reference NVMe). The same rows: **bit-exact** (`tests/models/qwen4_exp/test_ple_disk.py`). `xtx-xt-4x262k`: cold reads of 96-164k tokens ~14 % shorter (EXL3 3.05 bpw 164k 62.1 -> 53.4 s), agent turns 2-3 %; decode unchanged. `0`: the read before each forward. |
| `FREETOKEN_PLE_PREFILL_RANK0` | `1` | With `--ple-backend disk` at TP>1: only rank 0 reads a prefill's PLE rows from disk and broadcasts their bytes to the other ranks at the lookup (every rank stages every head, so the bytes are the same: **bit-exact**), instead of every rank reading the same rows at once from the same disk. Agent turns 4-7 % shorter on `xtx-xt-4x262k` (EXL3 3.05 bpw 0.466 -> 0.435 s, NVFP4 0.693 -> 0.662 s); decode and four requests unchanged. `0`: each rank reads its own. |
| `FREETOKEN_ROW_STORE_RINGS` | `4` | The disk row store (`--ple-backend disk`, every profile): a fill of 256 rows or more splits over this many io_uring rings, one thread each. One thread drove 240-290k reads a second whatever its queue depth; the reference machine's NVMe (PCIe 3 x4) takes ~490k a second from four. A row that crosses a 4 KiB page is read as its two pages, apart: on that disk, reads spanning two 4 KiB units, even 2.5 % of a batch, halved the whole batch's rate. The same bytes: **bit-exact** (`tests/kernels/test_row_store.py`). 9,600 random rows (a 600-token turn's) 40-42 -> 21-26 ms; on `xtx-xt-4x262k` EXL3 3.05 bpw agent turns 0.525 -> 0.494 s, NVFP4's (PCIe-bound) ~1-2 % with the tail tiles. `1`: one ring. |

## Speculative decoding with the MTP head (Qwen3.8-Flash-Next)

The checkpoint ships a multi-token-prediction head (`mtp.*`: one decoder layer with its own 512 experts). With it, a
decode step of one request verifies the head's guesses in the same forward: m rows (the last token, then m - 1
drafts), of which it keeps the matching prefix. How it works and what it costs:
[decisions.md](decisions.md#speculative-decoding-with-the-mtp-head), measurements:
[benchmarks.md](benchmarks.md#speculative-decoding-mtp-head). The profiles except `gre` turn it on (`FREETOKEN_MTP=1`,
`FREETOKEN_SPEC_VERIFY_M=4`); `rdna3/serve.sh --no-mtp` serves without it.

| Variable | Default | Effect |
|---|---|---|
| `FREETOKEN_MTP` | unset (`1` in the profiles) | `1`: load the MTP head and draft with it; its experts share the expert cache (an NVFP4 checkpoint's stacked bf16 head experts are quantized to NVFP4 at load, an EXL3 checkpoint's are read as they are). Only with `FREETOKEN_SPEC_VERIFY_M` > 1 (else a warning, and no head) and a checkpoint whose head experts are in one of those two forms (others are refused). |
| `FREETOKEN_SPEC_VERIFY_M` | `1` (`4` in the profiles) | The most rows a verify step runs (1 + drafts). With the head, `4` is the measured setting (the adaptive depth then picks 2-4 rows per request); greedy answers stay identical to plain decode with `FREETOKEN_INT8_DENSE=1`, as every profile sets (bf16 dense layers outside the GEMV table go through `F.linear`, whose sums can change with the row count) and the default fp32 GDN state (`FREETOKEN_MAMBA_SSM_DTYPE`). Without the head, `m` > 1 runs placeholder rows (a cost measurement only). |
| `FREETOKEN_SPEC_VERIFY_MS` | `1,2,..,M` with the head | The row counts a step may run, each with its CUDA graphs (counts above the smallest only for the batch sizes a verify step can have). Near a request's length limit a step runs no more rows than tokens left. |
| `FREETOKEN_SPEC_DYNAMIC` | `1` | Each request picks its rows per step (2 to M, at most 2 past `FREETOKEN_SPEC_BS_DEEP` requests; with `FREETOKEN_SPEC_BS_MAX` > 1, the most any of the step's requests wants) from its running acceptance per draft position and the step costs below: the count with the most expected tokens per millisecond (with two or more row counts above 1, as by default). `0`: always M. |
| `FREETOKEN_SPEC_COSTS` | measured, by card count | Step time per row count (ms; only the ratios matter): two cards (`xtx-xt`) `1:17.7,2:25.3,3:30.7,4:35.5`, one card (`xt`) `1:31,2:53,3:78,4:102`, where the extra rows' missing experts cross PCIe and the adaptive depth mostly keeps to 2 rows. Entries given here override. |
| `FREETOKEN_SPEC_BS_MAX` | `1`; `4` in `xtx-xt`, `xtx-xt-1m`, `xtx-xt-4x262k` | Verify drafts only while at most this many requests decode (at most `--cuda-graph-max-bs`, checked at start). With more, steps run one row per request, the head only writes its KV (so drafts stay good when a request is alone again) and scheduling overlaps as without the head. `2` against `1` (`xtx-xt`, an earlier build): two agents at ~100k of context decode 33.6-34.4 tok/s each instead of 30.8-31.1, 2-3 short requests finish 3-4 % sooner, 1 and 4 requests take the same time; a sweep to 248k ran without an out-of-memory retry. More than 2 rows each at four requests lose (an earlier build: four requests at 4 rows each 26.3 tok/s against 35.35 without verifying), hence `FREETOKEN_SPEC_BS_DEEP=2` beside it. Greedy answers as with `1`; past 8 rows per step answers can change. `xtx-xtx` and `xt-xt` leave it unset (not measured there). |
| `FREETOKEN_SPEC_BS_DEEP` | `FREETOKEN_SPEC_BS_MAX`; `2` in `xtx-xt`, `xtx-xt-1m`, `xtx-xt-4x262k` | More than 2 rows per request only while at most this many requests decode (at most `FREETOKEN_SPEC_BS_MAX`); past it, up to `FREETOKEN_SPEC_BS_MAX` requests, a step verifies 2 rows each and the head drafts one guess (1 row and no drafts if `FREETOKEN_SPEC_VERIFY_MS` has no 2). Each row of a wide step brings its own missing experts, so the second row pays where the third and fourth do not: four requests (NVFP4, `xtx-xt-4x262k`, one row count for every step) 31.3 tok/s each at 1 row, 35.2 at 2, 31.7 at 3, 30.4 at 4. `4` / `2` against `2` / `2` on `xtx-xt-4x262k`: three requests +6-9 % each, four +3-6 % greedy (-0.3 to +2.5 % at T 0.6), one request unchanged; `xtx-xt` and `xtx-xt-1m` gain at three requests too ([benchmarks.md](benchmarks.md#several-requests-and-agents-at-once-xtx-xt)). At the profile's own 1,050,000-token pool (EXL3 3.05 bpw, one run each): three requests 43.1 -> 45.9 tok/s each, four at T 0.6 38.2 -> 39.3; cold reads, decodes at 28k-130k of context and agent turns unchanged, 17 of 17 answers the same. Greedy answers the same on prompts read apart; four sent at once can differ, as between two runs without it (their prompts are read in one batch). At most 8 rows per step; a step of 3-4 requests no longer overlaps with the next one's scheduling, as a verify step must not. Two more CUDA graphs per card: ~280-380 MiB less VRAM free after the capture, the expert slots unchanged. |
| `FREETOKEN_MTP_KV_ONLY_STOP` | `1` | While more than `FREETOKEN_SPEC_BS_MAX` requests decode, the head's pass only writes its KV: it stops once the K/V and the index keys are written instead of attending and combining (nothing reads that output). The same KV. `0`: the whole pass. |
| `FREETOKEN_SPEC_GLUE_KERNELS` | `1` | A verify step's glue in kernels: the rollback copies (one kernel per state instead of ~6 ops), the token-pool writes, the kept counts of greedy rows, the head's rows and each chained guess's addressing; the acceptance log summed on the host. Each arm samples other texts (the draws fall differently), so single prompts move -9 to +18 %. At T 1.0 the same speed (an earlier build). `0`: the argmax. |

## Sampling

| Variable | Default | Effect |
|---|---|---|
| `FREETOKEN_FAST_TOPK_MAX` | `256` on ROCm, `0` elsewhere | When every request of the batch has a `top_k` of at most this value (the model's default is 20), the batch samples from its top-k candidates only: one `torch.topk` + one small kernel, ~0.07 ms per step, exact. Otherwise the batch takes the full-vocabulary path (below). |

On ROCm, top-k / top-p sampling never uses upstream's cooperative kernels: their multi-block rows spin on a barrier
that needs every block of a row running at once, which the cooperative launch does not give on this ROCm stack (they
hang on gfx1100), and with one block per row their top-p costs 10-60 ms per step. The full-vocabulary path takes an
exact threshold from a sort instead: 0.2 ms (1 request) to 1 ms (4 requests), the same kept set as the float64
definition, and for a given seed the same draws as upstream's kernels except when a draw lands within fp32 rounding of
a boundary between two tokens. One request without `top_k`, or with a larger one, sends its whole batch there. At a
tie on the k-th logit the top-k path keeps exactly k tokens, the sorted path keeps all the tied ones. The sorted path
is checked by kernel tests, not run on the agentic benchmark (greedy decoding and the model's default `top_k` of 20 do
not use it).

## Conversations kept in RAM

For hybrid models (attention + GatedDeltaNet, e.g. Qwen3.8-Flash-Next). When the GPU context memory is full, the least
recently used conversation parts are copied to pinned RAM instead of being dropped, and copied back when their
conversation returns. Exact: a conversation brought back gives the same greedy answer as one that never left (four
conversations checked). Checked for exactness, not on the agentic benchmark.

| Variable | Default | Effect |
|---|---|---|
| `FREETOKEN_HOST_KV` | unset | `1`: enable. For several conversations that together outgrow the GPU pool, such as parallel sub-agents: a returning conversation is copied back instead of read again from scratch ([how-it-works.md](how-it-works.md#conversations-kept-in-ram)): four agents with 82-117k-token conversations, 3 turns each, got their first token in ~2 s instead of ~47 s after the first reads. No gain for a single conversation that fits the GPUs; costs the pinned RAM below. |
| `FREETOKEN_HOST_KV_TOKENS` | `262144` | RAM tier size in tokens (Qwen3.8-Flash-Next, TP=2: 4.91 + 4.59 GiB pinned for the two ranks with the MTP head, 4.64 + 4.32 without, with the snapshots below). |
| `FREETOKEN_HOST_KV_SNAPSHOTS` | `24` | GatedDeltaNet state snapshots kept in RAM (50-65 MB each at TP=2). |
| `FREETOKEN_HOST_KV_LOG` | unset | `1`: log every move to and from RAM. |

Beyond the GPU pool + the RAM tier, the least recently used conversations are dropped as upstream does.

## Scheduling

| Variable | Default | Effect |
|---|---|---|
| `FREETOKEN_DECODE_INTERLEAVE` | `0` | `N`: after each prefill chunk, the requests already decoding get up to N decode steps before the next chunk. Keeps other agents moving during a long read, but measured to hurt the short prefills of agent turns: keep `0`. |
| `FREETOKEN_VRAM_MARGIN_MIB` | `512` on ROCm, `0` elsewhere | Once the engine is built, cap the torch allocator at the card's VRAM minus what lives outside torch then (HIP runtime, RCCL, loaded kernel modules, scratch, a desktop's buffers: the card's used VRAM is read from sysfs, since the free memory HIP reports leaves the graphics stack out) minus this margin. The same compiled kernel with the same arguments: **bit-exact** by construction (`tests/kernels/test_triton_fast_launch.py`). A launch took ~18 us of host time in isolation (~10 us this way) and ~50 us in the server, and a short agent turn launches ~1,550: EXL3 one-word turns 0.235 -> 0.214 s on `xtx-xt-4x262k`, NVFP4 (PCIe-bound) 0.260 -> 0.255 s. A launch hook (a profiler), a pre-run hook, an argument type the key does not cover, or a Triton other than 3.8.0 takes Triton's path (no `Triton launches: fast path` line in the log then). `check`: also runs Triton's binder at every launch and raises if it would pick another kernel (validation). `0`: Triton's path. |
| `FREETOKEN_MLOCK` | `1` | Lock the process's memory once the model is loaded (`mlockall`, current and future pages, on fault), so that with `vm.compact_unevictable_allowed=0` the kernel's memory compaction leaves the pages the GPU driver maps alone; each move stopped the GPU queues for seconds ([troubleshooting.md](troubleshooting.md#long-pauses-in-the-middle-of-a-run)). Skipped, with a log line, under a finite `RLIMIT_MEMLOCK`. `0`: off. |

## Diagnostics (off by default)

| Variable | Effect |
|---|---|
| `FT_STATS_EVERY=N` | Every N graph-replayed decode steps, log the host step period vs the GPU time of the forward. |
| `FT_MOE_STATS=1` | With `FT_STATS_EVERY`: also the expert-cache miss counters. |
| `FT_PROF_STEPS=N`, `FT_PROF_START=S` | torch.profiler over N decode steps from step S; tables and a chrome trace in `FT_PROF_DIR`. |
| `FREETOKEN_DUMP_PROMPT_TOPK=<dir>` | Tests only: rank 0 saves the top-40 log-probabilities and the input ids of every prefill chunk to `<dir>/prompt-<n>.pt` (teacher-forced comparisons; send raw completions, a chat user turn mostly measures `<\|im_end\|>`). Needs `FREETOKEN_MTP=0`; at 1M of context, `--max-prefill-length 4096`. |
| `FT_PROF_EAGER=1` | Also profile eager decode (run with `--cuda-graph-max-bs 0`): ROCm's profiler does not see kernels replayed from a CUDA graph. |
| `FT_PROF_STACK=1` | With `FT_PROF_STEPS`: also record Python stacks and input shapes; the chrome trace then ties each kernel to the line that launched it (ops by input shape in `rank<r>_ops_by_shape.txt`). |
| `FREETOKEN_SPEC_TIMING=N` | Every N decode steps, the GPU and host time of each phase (forward, verify, MTP head, draft chain) per (requests, rows); one stream sync per report. |
| `FREETOKEN_SPEC_STALL_MS` | `500`; with `FREETOKEN_SPEC_TIMING`, every decode step whose GPU or host time, or distance to the previous step, exceeds it is logged on its own with its phases and the time of day (every rank): to catch the occasional stall. |
| `FREETOKEN_PLE_FILL_TIMING=N` | Every N decode steps, the host's wait for the step's tokens and the PLE disk fill time after it (the GPU idles through the fill when stream memops are unavailable). |

`FT_PROF_DIR` defaults to `./ftprof`, i.e. `/opt/FreeToken/ftprof` inside the container, which is lost when the
container stops: set `FT_PROF_DIR=/root/.cache/freetoken-rdna3/ftprof` to keep it in the kernel-cache volume, or
`docker cp` it out first.

## PyTorch TunableOp

Not used: tuning the dense GEMMs of the 16k-token prefill chunks gained 1.5-1.7 % on those GEMMs and < 0.2 % on
prompt reading ([journey.md](journey.md#17-dropped-along-the-way)). Never enable tuning in service
(`PYTORCH_TUNABLEOP_TUNING=1`): each new prompt length would be tuned on the spot (16 s prefills).

## Container settings the engine does not check

`PYTORCH_ALLOC_CONF=expandable_segments:True` and `OMP_WAIT_POLICY=PASSIVE` (set by `serve.sh`; the engine also turns
expandable segments on by itself when neither `PYTORCH_ALLOC_CONF` nor `PYTORCH_CUDA_ALLOC_CONF` is set; without expandable
segments the allocator's cache filled the free VRAM and every 14-16k-token prefill chunk past ~26k of context failed
once and retried after emptying it, with or without the MTP head and with a larger margin too), an explicit
`HIP_VISIBLE_DEVICES` (rank 0 first), `--ulimit memlock=-1` (pinned RAM for the experts and the RAM tier) and
`--ipc=host` (shared memory between the two ranks). `TVM_FFI_CACHE_DIR` (set by the image and `serve.sh`) keeps the JIT
modules in the per-image cache volume: without it they are rebuilt at every start (first request ~10 s instead of
1.3-1.9 s).
